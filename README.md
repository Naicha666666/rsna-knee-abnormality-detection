## R 线：CoAtNet-384 study-window MIL（`src/raptor.py`）

### 为什么另开一条线
DINOv2 六槽线从 v8 到 v14 做了七组单变量消融（种子集成、分辨率/覆盖、epoch 选择规则、ViT-B、折数、槽位死槽修复、header 恢复标志），**全部落在 ±0.004 的 run-to-run 噪声内**（噪声本身由 v6/v7 同配置换种子标定）。同时核实真实榜面后发现，公开计分最高的 notebook（DINOsaur V4/V10，0.936）里单独一个 CoAtNet-384 分支就有 **0.914**，说明瓶颈是**表示能力与输入分辨率**，不是槽位怎么切。R 线因此换骨干（CoAtNet-384，非 DINOv2）、换聚合方式（无槽/无解剖先验，纯 study-window MIL），第一次全量提交（R1）就拿到 **0.891**，自研预处理下最好 **R3 = 0.897**。当前最好成绩已转到 C 线（自研单模 C6 = 0.935，与公开 fork 融合 0.942）。完整推导过程见 `LOG.md` "R 线开工"一节。

### 槽定义（复用 `config.SLOTS`，索引对两条线通用）
六个槽由 `(解剖平面, 是否流体敏感, 是否脂肪抑制)` 三元组定义。**槽 3 是 v13 修复过的版本**——原始 `("Sagittal", 1, 0)` 在全部 4407 个 study 里匹配 0 条序列（该组合在这批数据的 CSV 标注下不存在），已替换为覆盖率更高的轴位结构序列：

| 索引 | 槽名 | (平面, 流体敏感, 脂肪抑制) | study 覆盖率 |
|---|---|---|---|
| 0 | SAG_FLUID_FS | (Sagittal, 1, 1) | 94.2% |
| 1 | COR_FLUID_FS | (Coronal, 1, 1) | 96.4% |
| 2 | AX_FLUID_FS | (Axial, 1, 1) | 100.0% |
| 3 | AX_STRUCT | (Axial, 0, 0) | 19.4%（六槽中最稀疏） |
| 4 | COR_STRUCT | (Coronal, 0, 0) | 77.3% |
| 5 | SAG_STRUCT | (Sagittal, 0, 0) | 96.8% |

R 线通过 `config.RAPTOR_SLOTS`（槽索引的子集/顺序）决定实际使用哪几个槽，独立于 DINOv2 线的 `SlotHead` 解剖先验。

### R1 / R2 / R3 配置与结果对照
384px 下的内存代价比 168px 高 (384/168)² ≈ 5.2 倍，缓存预算是这条线的硬约束（详见下方"训练/推理缓存解耦"）：

| | R1 | R2 | R3 |
|---|---|---|---|
| `RAPTOR_SLOTS` | (0,1,2) 3个流体敏感脂抑槽 | 全部6槽（0-5） | (0,1,2) 回到3槽 |
| 片/序列 | 6 | 4 | **8** |
| 训练总切片数/study | 18 | 24 | 24 |
| `RAPTOR_CACHE_BUDGET_GB` | 12.0（实际10.89GB） | 16.0（实际14.53GB） | 16.0（实际14.53GB） |
| `RAPTOR_K_EVAL` | 12 | 999（哨兵=穷举） | 999 |
| SWA | 无 | 有 | 无 |
| **derived-holdout AUC**（同一866-study划分） | 0.8302 | **0.8109** | **0.8318** |
| **公开榜 LB** | **0.891** | **0.874** | **0.897** |

**这三次跑出了一个干净的归因**：R2 相对 R1 同时改了三件事（槽数、深度、SWA），LB 掉了 0.017，无法归因。R3 因此设计成"与 R2 总切片数和缓存**完全相同**，只是集中在 3 槽而非摊到 6 槽"：

- **R3 vs R2（同预算，集中 vs 摊开）：+0.0209** → 同样的内存，集中在 3 个流体敏感脂抑序列远好于摊到 6 个槽。
- **R3 vs R1（唯一变量=深度 6→8）：+0.0016** → 基本持平，深度的边际收益已经很小。
- 合起来：**R2 的退步几乎全部来自"新增 3 个结构槽"，不是被挤压的深度**。这与 v13 的覆盖率数据吻合——`AX_STRUCT` 只有 19.4% 的 study 有内容，大量 study 在新槽上是空位，真正被稀释的是每个 study 的有效窗口预算。

**关于"64片/5槽"这个数字**：核对 DINOsaur V4 源码后发现它来自参考notebook的**推理段**（对很小的测试集逐 study 解码），不是可保存在内存里训练全量语料的缓存预算——按 384px 实算，12GB 在 4407 个 study 下所有槽加起来只买得起约 20 张切片。不要照抄这个数字。

### 训练/推理缓存解耦
训练缓存要一次性放下全部 ~4407 个 study 供多轮 epoch 复用，是内存瓶颈；**推理（测试集）不需要**——隐藏测试集通常很小，可以承受远高于训练时的单序列切片密度而不触碰 `RAPTOR_CACHE_BUDGET_GB`。`build_window_cache(..., force_n_per=...)` 让测试集解码绕开训练时的容量规划器；`RAPTOR_EVAL_SLICES_PER_SERIES=20` 配合 `RAPTOR_K_EVAL=999`（`eval_picks` 一旦候选窗口数超过 k 就直接返回全部窗口）→ **推理时窗口覆盖接近穷举**，且完全不影响训练缓存大小。

### SWA + BatchNorm 重校准
`RAPTOR_USE_SWA=True` 时，训练后半程（`RAPTOR_SWA_START_FRAC=0.5`）对每个 epoch 的权重做递增平均。PyTorch 官方的 `swa_utils.update_bn` 假设单输入 forward，我们的 `RaptorClassifier.forward(x, kmask)` 是双参数，无法直接套用，因此 `raptor._recalibrate_bn` 手写了同一套逻辑（重置 BN running stats，`momentum=None` 做累积平均的 forward-only 遍历）。训练结束后 SWA 权重和历史最佳单 epoch 权重都在 holdout 上评估，**分数高的那个才会被采用**，不预设 SWA 一定更好。

## C / L 线：公开语料 + LLM 软标签（当前主线）

C 线挂 `dreaddevelopment/knee-raptor-corpus`（+ ext）的 uint8 memmap，训练时解码耗时 0、没有 `RAPTOR_CACHE_BUDGET_GB` 天花板。L 线把 4407 份报告用 LLM 重标，经 `config.SOFT_LABEL_PARQUETS` 与正则抽取器做**概率平均**（不是 rank 平均：后者会把每列均值钉在 0.5，当 BCE 目标是失真）。

**风险 / 约束记录**
- R3 总时长已到 ~5.3h，加隐藏测试推理后距 9h 上限余量收窄；C 线因解码=0 更宽裕（C2 实测 366 min）。
- `RAPTOR_RES` 不可随意改：CoAtNet-rmlp 的相对位置表锁死在 384 网格（本地实测非 384 输入直接抛形状错），与 DINOv2 的可插值 pos_embed 不同。
- T4 上必须用 compute capability 选 fp16，不能信 `is_bf16_supported()`（C1 v2/v3 两次 OOM）。
- **bf16 设备（Ampere+ / L4 / A100 / R9700）上 `GradScaler` 是禁用的，等于没有 inf/nan 跳步**：`clip_grad_norm_` 拿到 nan 梯度会算出 nan 范数，再把全部梯度乘以 nan，一步永久毁掉权重。C5 就是这样在 epoch 5 变成 loss=nan 并再没恢复。`corpus.py` 现在在 scaler 禁用时自己守 `torch.isfinite(gn)` 并计数 `skip=N`；fp16 路径保持逐字节不变，T4 结果仍可比。CPU 最小复现见 `scratchpad/nan_guard_test.py`。
- 长跑必须能中途落盘：`train_on_corpus(..., ckpt_path=)` 现在每次刷新最好分就写一次，别再把十几个 epoch 押在"跑到底"上。
- **MIOpen 在 gfx1201 上对 bf16 深度卷积回退到 naive 参考核**，比 PyTorch 原生核慢 3–4 倍（单层实测 52 vs 15 ms）。只替换这 8 个深度卷积即可，**全局关掉 MIOpen 反而更慢**（1×1 卷积变慢）。另实测 **fp16 + MIOpen 在 stride 1 深度卷积上前向结果是错的**（相对误差 2–3），日后若改 fp16 必须避开 MIOpen。bf16 的梯度经 fp32/fp64 对照确认**是对的**（LOG #384）。
- 语料几何由 `RSNA_CORPUS_SLOTS=44|64` 选（默认 44）。选错不会静默——`open_corpus` 会在深度对不上时硬退出。**C5 跑完前不要往 R9700 上再 scp `config.py` / `corpus.py`**：那边配置是 64 片 / k=12 / 16 ep 的独立副本。
